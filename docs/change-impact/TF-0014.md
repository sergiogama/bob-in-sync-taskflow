# Change Impact Analysis

**Reference:** TF-0014  
**Date:** 2026-08-29  
**Status:** Pending Implementation Approval  
**Analyst:** Bob (automated analysis)

## Change Request

Add a `priority` attribute to tickets with the canonical values `LOW`, `MEDIUM`, `HIGH`, and `CRITICAL`. Tickets with priority `CRITICAL` must have an SLA deadline automatically calculated as 4 hours after ticket creation. The ticket list and ticket detail pages must display the priority. Tickets that exceed their SLA deadline without being `RESOLVED` or `CLOSED` must be visually identified as overdue. The dashboard must surface visibility into critical and overdue tickets.

Existing tickets must continue to work correctly after this change is introduced.

---

## Business Outcome

- The support team gains a standardised way to classify urgency on maintenance requests.
- Critical work items are automatically assigned an SLA deadline, reducing manual tracking.
- Overdue critical tickets are immediately visible in the dashboard and ticket views, enabling faster escalation.
- All historical tickets are preserved and remain fully usable after the change.

---

## Clarifications and Assumptions

The following questions and assumptions should be validated with the business before implementation begins.

1. **Default priority for new tickets.** The request does not specify a default. Assumption: `MEDIUM` is the default when no priority is provided, following the precedent set by the `status` field defaulting to `OPEN`.

2. **Default priority for existing tickets (migration).** Existing tickets will be backfilled with `MEDIUM` priority during migration. This avoids nullable priority values, keeps the data model consistent, and ensures all tickets follow the new priority model after deployment.

3. **SLA deadline for non-CRITICAL priorities.** The request only specifies an SLA for `CRITICAL`. No SLA deadline should be stored for `LOW`, `MEDIUM`, or `HIGH` tickets. The `sla_deadline` column should be nullable.

4. **SLA deadline recalculation on priority change.** If a ticket is created as `CRITICAL`, `sla_deadline` is set to `created_at + 4 hours`. If an existing ticket is later changed to `CRITICAL`, `sla_deadline` is recalculated as the priority change timestamp + 4 hours. If a `CRITICAL` ticket is changed to `LOW`, `MEDIUM`, or `HIGH`, `sla_deadline` is cleared.

5. **"Overdue" definition.** Assumption: a ticket is overdue when `sla_deadline IS NOT NULL` AND `NOW > sla_deadline` AND `status NOT IN ('RESOLVED', 'CLOSED')`. This aligns with the stated requirement.

6. **Overdue display scope.** The request says the dashboard must show overdue tickets. Assumption: a new dashboard counter or section is added (not a separate page). The ticket list should also visually flag overdue rows.

7. **Priority filter on ticket list.** Not explicitly mentioned in the request but logically expected by the team. This should be confirmed before implementation.

8. **Who can set/change priority.** In v1.0 all authenticated users have identical permissions. No RBAC change is assumed to be required for this feature.

9. **Time zone for SLA calculation.** `CURRENT_TIMESTAMP` in SQLite is UTC. The `+4 hours` deadline should be calculated as UTC. The frontend should apply the same normalization used for other date fields.

## Database and Migration Impact

### Schema Changes Required

```sql
-- Add to the tickets table
priority     TEXT DEFAULT 'MEDIUM'
               CHECK (priority IN ('LOW', 'MEDIUM', 'HIGH', 'CRITICAL')),
sla_deadline TEXT   -- NULL for non-CRITICAL or if not yet set
```

A new index on `priority` is advisable given the dashboard filtering use case:

```sql
CREATE INDEX IF NOT EXISTS idx_tickets_priority ON tickets(priority);
```

### Migration Risk — CRITICAL

TaskFlow v1.0 **does not have a migration framework**. The schema is applied with `CREATE TABLE IF NOT EXISTS` on startup. Adding columns to an existing table with `ALTER TABLE` is not handled automatically.

The production database at `data/taskflow.db` and any deployed database will **not receive the new columns** on a standard application restart. Manual `ALTER TABLE` statements must be run against each environment before deploying the updated application:

```sql
ALTER TABLE tickets ADD COLUMN priority TEXT DEFAULT 'MEDIUM'
  CHECK (priority IN ('LOW', 'MEDIUM', 'HIGH', 'CRITICAL'));
ALTER TABLE tickets ADD COLUMN sla_deadline TEXT;
CREATE INDEX IF NOT EXISTS idx_tickets_priority ON tickets(priority);
```

**If these statements are not run before deployment, the application will fail at runtime** on any query that references the new columns.

SQLite `ALTER TABLE … ADD COLUMN` permits adding a `NOT NULL` column only if a `DEFAULT` is specified, which is satisfied by the proposed schema. This makes backfilling existing rows automatic and safe — they will receive `DEFAULT 'MEDIUM'` for `priority` and `NULL` for `sla_deadline`.

> **Recommendation:** Implement a lightweight migration script (e.g., `server/scripts/migrate.js`) as part of this change, or document the manual migration steps explicitly in the deployment runbook.

## API Impact

### Modified endpoints

| Endpoint | Change |
|---|---|
| `POST /api/tickets` | Body accepts new optional `priority` field (default `MEDIUM`). Response includes `priority` and `sla_deadline`. |
| `PUT /api/tickets/:id` | Body accepts `priority` field. Validation enforces allowed values. |
| `GET /api/tickets` | Response objects include `priority` and `sla_deadline` fields. |
| `GET /api/tickets/:id` | Response includes `priority` and `sla_deadline`. |
| `GET /api/dashboard` | Response `counts` object should be extended to include `CRITICAL` count and `overdue` count. |

### Breaking change assessment

Existing API consumers that do not send `priority` will receive the default value. **Responses will include two new fields** (`priority`, `sla_deadline`). This is additive and backward compatible for consumers that ignore unknown fields, but technically breaks strict schema validation on consumers that do not tolerate extra fields.

## Testing Impact

### Existing tests at risk

| Test | Risk | Reason |
|---|---|---|
| `lists, searches, and filters tickets` | LOW | Asserts exact ticket count (12). If seed data is updated to add a `priority` column, the INSERT signature changes but the count remains the same. No breakage expected if seed is updated correctly. |
| `creates, edits, assigns, and retrieves a ticket` | MEDIUM | Does not send `priority` — must still pass with the default value. Response will include new fields; test does not assert on them, so no breakage expected. Seed update required. |

| `validates invalid ticket status` | NONE | Unrelated to this change. |

### New tests required

1. **`creates a ticket with LOW priority`** — POST with `priority: 'LOW'`, assert `priority === 'LOW'` and `sla_deadline === null`.
2. **`creates a CRITICAL ticket and sets sla_deadline`** — POST with `priority: 'CRITICAL'`, assert `sla_deadline` is a valid datetime approximately 4 hours after `created_at`.
3. **`editing priority to CRITICAL does not change sla_deadline`** — PUT to change priority after creation, assert `sla_deadline` is unchanged (per Assumption 4).
4. **`validates invalid priority value`** — POST with `priority: 'URGENT'`, assert HTTP 400 with an appropriate error message.
5. **`dashboard counts include overdue and critical`** — assert the response shape includes `critical` and `overdue` keys.
6. **`omitting priority uses default value MEDIUM`** — POST without `priority`, assert `priority === 'MEDIUM'`.

## Risks and Regression Areas

| Area | Risk | Description |
|---|---|---|
| **No migration framework** | HIGH | Manual SQL migration required before deployment. If skipped, the application crashes on startup with column-not-found errors. |
| **Seed data coupled to tests** | MEDIUM | `server/database/seed.js` must be updated to include `priority` in the ticket INSERT. The INSERT statement currently uses positional parameters — adding a column requires updating every seed row tuple. |
| **Dashboard count shape change** | MEDIUM | The test `returns dashboard counts and users` asserts `Object.values(counts).reduce(sum) === 13`. If new keys (`critical`, `overdue`) are added to the `counts` object, this sum will no longer equal 13. The assertion must be updated to sum only status counts. |
| **`ticketSelect` query breadth** | LOW | The `ticketSelect` constant is a shared SQL fragment used in `list()`, `findById()`, and indirectly in `create()` (via `findById`). Adding columns here propagates to all read paths simultaneously — low regression risk but requires a single careful edit. |
| **SLA deadline is server-side UTC** | LOW | The `sla_deadline` is computed and stored as UTC text. The frontend must normalize it the same way other date fields are normalized. If the frontend displays raw values without normalization, the time will appear incorrect in non-UTC timezones. |
| **`priority` filter on ticket list** | LOW | If a `priority` query parameter is added to `GET /api/tickets`, the `list()` method in `ticketModel` must be extended. This is isolated but must not break the existing `search` + `status` filter logic. |
| **Backward compatibility of `PUT /api/tickets/:id`** | MEDIUM | The current update endpoint performs a full field replacement. If `priority` becomes a required field and an existing client (e.g., a script or integration) sends a PUT without it, the request will be rejected. Recommendation: make `priority` optional in updates, defaulting to the current value if omitted — but this changes the semantics of the endpoint. |

## Risk Level

### **MEDIUM**

**Reasons:**

- The schema change is additive (new nullable columns) and backward compatible at the SQLite level.
- However, the **absence of a migration framework** elevates deployment risk significantly. A deployment without the manual `ALTER TABLE` will cause runtime failures.
- The **dashboard test assertion** will break as written unless updated to account for new count keys.
- The **seed data** requires a structural change (new positional parameter in the INSERT), which affects all 12 seed rows and must be done carefully.
- The functional scope is moderate: one new data attribute, one computed field, and visual indicators across four pages.

The change does not touch authentication, sessions, or permissions. It does not introduce new routes. The core data model change is confined to the `tickets` table. These factors keep the risk from reaching HIGH.
