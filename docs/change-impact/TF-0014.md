# Change Impact Analysis

**Ticket:** TF-0014  
**Title:** Add ticket priority and SLA management  
**Status:** OPEN  
**Created by:** Maria Santos  
**Assessment date:** 2026-08-29  

---

## Change Request

Add a `priority` attribute to tickets with the values `LOW`, `MEDIUM`, `HIGH`, and `CRITICAL`. Critical tickets must have an SLA deadline automatically calculated as 4 hours after ticket creation (or after the moment a ticket's priority changes to CRITICAL). The ticket list and ticket detail pages must display the priority. Tickets that exceed their SLA deadline without being resolved or closed must be clearly identified as overdue. The dashboard must provide separate visibility for critical and overdue tickets. Existing tickets must continue to work correctly after this change.

---

## Business Outcome

- Support teams can classify tickets by urgency, enabling triage and response prioritization.
- CRITICAL tickets get an automatic 4-hour SLA clock, surfacing breach risk before it becomes a problem.
- The dashboard provides two new at-a-glance metrics — CRITICAL count and OVERDUE count — allowing managers to act on the most urgent situations immediately.
- All existing tickets remain functional; the migration default (MEDIUM) preserves existing workflows.

## Database and Migration Impact

### Schema Changes

```sql
-- New columns to add to the tickets table:
priority     TEXT NOT NULL DEFAULT 'MEDIUM'
             CHECK (priority IN ('LOW', 'MEDIUM', 'HIGH', 'CRITICAL'))
sla_deadline TEXT   -- nullable; ISO 8601 UTC string; only set for CRITICAL tickets

-- New indexes (recommended):
CREATE INDEX IF NOT EXISTS idx_tickets_priority     ON tickets(priority);
CREATE INDEX IF NOT EXISTS idx_tickets_sla_deadline ON tickets(sla_deadline);
```

### Migration Requirement

TaskFlow v1.0 has **no migration framework**. Schema is applied via `db.exec(schema)` at startup using `CREATE TABLE IF NOT EXISTS`, which does **not** alter existing tables.

**Required approach:** After `db.exec(schema)` in `server/database/index.js`, apply a safe migration block using `PRAGMA table_info` or catch duplicate-column errors:

```js
// Apply safe ALTER TABLE migrations for existing databases
for (const stmt of [
  `ALTER TABLE tickets ADD COLUMN priority TEXT NOT NULL DEFAULT 'MEDIUM'
   CHECK (priority IN ('LOW', 'MEDIUM', 'HIGH', 'CRITICAL'))`,
  `ALTER TABLE tickets ADD COLUMN sla_deadline TEXT`
]) {
  try { db.prepare(stmt).run() }
  catch (e) { if (!e.message.includes('duplicate column')) throw e }
}
```

Existing tickets will receive `priority = 'MEDIUM'` automatically via the column's `DEFAULT` clause (SQLite applies the default to rows added by `ALTER TABLE ADD COLUMN` where the column is `NOT NULL` with a default). The `sla_deadline` for existing tickets will be `NULL`, which is correct.

**Test databases** (`:memory:`) are always fresh and do not require the migration block to function, but including it is harmless.

### New Tests to Write (~12 test cases)

**Priority validation:**
1. Create ticket with no `priority` field → `priority === 'MEDIUM'` and `sla_deadline === null`.
2. Create ticket with `priority: 'LOW'` → `priority === 'LOW'`, `sla_deadline === null`.
3. Create ticket with `priority: 'HIGH'` → `priority === 'HIGH'`, `sla_deadline === null`.
4. Create ticket with `priority: 'CRITICAL'` → `priority === 'CRITICAL'`, `sla_deadline` is a timestamp ~4 hours from now.
5. Create ticket with `priority: 'URGENT'` → HTTP 400 with error matching `/valid priority/i`.

**SLA calculation:**
6. Create CRITICAL ticket → `sla_deadline` is approximately `now + 4 hours` (allow ±5 second tolerance).
7. Update MEDIUM ticket to CRITICAL → `sla_deadline` is set to `updated_at + 4 hours`.
8. Update CRITICAL ticket to MEDIUM → `sla_deadline` is cleared (null).

**Dashboard counts:**
9. `counts` object contains `CRITICAL` key with correct count.
10. `counts` object contains `OVERDUE` key; RESOLVED/CLOSED tickets with past `sla_deadline` are excluded.

**Migration/backward compatibility:**
11. All 12 seed tickets have `priority === 'MEDIUM'` after seeding.
12. All 12 seed tickets have `sla_deadline === null` after seeding.

## Risks and Regression Areas

| Risk | Severity | Area | Detail |
|------|----------|------|--------|
| **Database migration failure** | HIGH | Infra/Ops | No migration framework. Existing `data/taskflow.db` will not receive new columns on restart unless `ALTER TABLE` bootstrap is added. Silent failures possible if the bootstrap is missing. |
| **Test assertion breakage (dashboard sum)** | HIGH | CI/Tests | The current `reduce` assertion will immediately fail. Must be fixed before merging. |
| **`docs/overview.md` contradiction** | HIGH | Documentation | v1.0 scope statement explicitly excludes the features being added. Creates confusion for all readers until corrected. |
| **SLA timestamp timezone mismatch** | MEDIUM | Backend/Frontend | SQLite stores timestamps in UTC; JavaScript `new Date()` is local-time-aware. SLA comparison must use UTC consistently. The existing `formatDate()` pattern already handles this but must be verified for `sla_deadline`. |
| **Dashboard metric grid layout** | MEDIUM | Frontend/UX | Expanding from 4 to 6 metric cards requires CSS grid changes and responsive breakpoint adjustments. Untested grid dimensions may break narrow-viewport layouts. |
| **Overdue count overlap confusion** | MEDIUM | API/Tests | `CRITICAL` and `OVERDUE` counts overlap with status-based totals. Any code that sums all dashboard keys will produce incorrect results. The existing test does exactly this. |
| **Seed data INSERT mismatch** | MEDIUM | Tests | If `seed.js` is not updated alongside the schema, the INSERT will fail on the NOT NULL `priority` column, breaking all tests. |
| **Form allows SLA deadline manipulation** | LOW | Frontend/Security | The SLA deadline must be server-computed. If the frontend form inadvertently sends `sla_deadline` in the payload, the service must ignore it. The service layer should compute SLA exclusively. |
| **Priority not in existing list/filter logic** | LOW | Backend | If `ticketModel.list()` filters by query params generically, an unknown `priority` value from query string could cause a SQL error or silent misbehavior. Service must validate the filter value before passing to model. |

## Risk Level

**HIGH**

**Rationale:** Three independent HIGH-severity failure vectors exist before any optional risk is considered:
1. The absence of a database migration framework makes it possible to deploy the change against an existing database without the new columns, causing runtime failures.
2. The existing automated test for dashboard counts will fail immediately due to the overlapping-key structure of the new response.
3. Core project documentation (`docs/overview.md`) contradicts the feature being added and will mislead developers and stakeholders until corrected.

The feature additions themselves are straightforward, but the migration path and test corrections are non-trivial and must be addressed as part of implementation.
